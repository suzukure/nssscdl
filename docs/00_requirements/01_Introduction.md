# 1. はじめに

## 1.1 目的
本システムは、小規模な個人レッスンスクールにおける月次スケジュール公開、生徒自身による予約・キャンセル、スクール側のスケジュール管理、必要最小限の通知・アカウント管理を行う。

初期想定はスクール管理者1名、生徒約20名である。決済・請求・会計は扱わない。

## 1.2 要求階層
要求は次の階層で管理する。

**POL（System Policy） → BR（Business Rule） → REQ（Requirement） → AC（Acceptance Criteria）**

CONは技術・運用上の制約、OOSは初期リリース対象外を表す。

## 1.3 利用者ロール
- **生徒**：自分の予約、キャンセル、プロフィール、認証を扱う。
- **スクール管理者**：講師・運営者として、月間スケジュール、生徒支援、欠席、スクール都合キャンセル等を扱う。
- **システム保守担当者**：Cloudflare等の技術基盤、監視、バックアップ、障害復旧を扱う。専用のアプリケーション内保守担当者画面は初期リリースでは持たない。

同一人物が複数ロールを担うことは許容するが、権限概念は分離する。

# 2. システム全体方針

## POL-001 必要最小限・低運用負荷
現在の業務に必要な機能に絞り、手作業より自動処理・自動削除を優先する。将来拡張の余地は残すが、仮想的な将来需要のために初期リリースを複雑化しない。過剰な監視、RBAC、分析機能を避け、可能な限りマネージド／サーバーレスを利用する。

## POL-002 無料枠優先・Must要件優先
現在規模では原則無料枠内での運用を目指す。ただしセキュリティ、プライバシー、整合性、バックアップ、RPO/RTO、予約・キャンセル・認証等のMust要件を無料枠維持のために弱めない。容量逼迫時は自動削除・抑制を先行し、継続的超過時のみ人が有料化・Provider変更等を判断する。自動有料化は行わない。

## POL-003 業務状態と外部連携の分離
本システム内部で正常に確定した業務状態を正とする。メール、Googleその他の外部連携は補助機能であり、外部連携失敗によって確定済みの予約・キャンセル等を暗黙に取消、Rollback、再実行しない。必要な外部操作は冪等性を考慮する。

## POL-004 個人情報最小化
収集・保存・送信する個人情報は業務上必要な最小限とし、不要な複製を避ける。ログや外部Providerにも必要最小限のみ渡す。利用目的終了後は削除・匿名化し、分析目的だけの匿名データ蓄積は行わない。

## POL-005 通知は即時性、システム画面は確実性
システム内部の確定業務状態を正とし、システム画面はその状態を利用者が確認する正本表示とする。メール等の外部通知は素早く気付かせる補助チャネルとし、業務状態の唯一の記録にはしない。マジックリンク・招待リンクは認証入口としての例外である。

## POL-006 ロール分離と最小権限
生徒、スクール管理者、システム保守担当者の権限を分離し、必要最小限を付与する。Google認証成功だけで管理者権限を与えない。重要操作はActor IDを保持する。

## POL-007 外部Provider依存の局所化
Resend、Google認証等のProvider固有処理は局所化し、将来交換可能とする。主要基盤としてCloudflareを選定しているため、完全なクラウド中立性は要求しない。

## POL-008 競合時の確定状態優先
同一業務対象への競合操作は、最初に正常Commitされた状態を優先する。後続操作は最新状態を再読込・再検証し、確定状態を暗黙に上書きしない。競合した利用者には状態変化を明示する。複数変更の一部だけ競合した場合、原則として部分適用せず再確認に戻す。

## POL-009 業務上異なる意味を別の状態として扱う
業務上意味の異なる状態・操作を、便宜上同じデータや状態として表現しない。例：キャンセルと欠席、生徒予約と管理者確保、利用停止と退会、予約状態と月間回数算入可否、連絡先メールとGoogle認証メール。

## POL-010 既定ルールと例外を分離する
通常運用は単純な既定ルールで表現し、例外は明示的な例外設定として扱う。例外によって基本マスタを不用意に変更しない。

## POL-011 セルフサービスを基本とし必要な利用支援を可能とする
生徒自身による操作を基本としスクール管理者の作業を増やさない。一方、利用者支援が必要な場合は管理者が必要範囲で代理支援できる。ただし本人確認・所有確認等のセキュリティ要件は代理操作でも省略しない。

## POL-012 サービス提供時間と有人保守時間の分離
本システムは原則24時間利用可能なサービスとして提供するが、24時間の有人保守体制は要求しない。サービス提供時間、自動監視・自動復旧、有人保守対応時間を別概念として定義し、障害時の対応時間およびRTOは有人保守対応時間帯を考慮する。

## POL-013 重要な管理操作の説明性と監査可能性
スクール管理者が予約、利用者、公開スケジュールその他の重要な業務状態へ影響を与える操作を行う場合、実行前に目的と主な影響を理解できる情報を提示する。取消、キャンセル、利用停止、既存設定への非遡及等の影響がある場合は対象と影響を明示して確認を求める。実行後は必要最小限の情報により、誰が・いつ・何を行ったかを追跡可能とする。

# 3. 初期導入
- 新しい月の予約受付を新システムで開始するタイミングをCutoverとする。
- 旧運用の過去予約履歴は移行しない。
- 生徒は自ら最低限の情報を登録する。管理者の初期作業は原則として案内に留める。
