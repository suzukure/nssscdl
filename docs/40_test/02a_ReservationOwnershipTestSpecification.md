# 予約所有者同一性テスト仕様

## 1. 位置づけ

要求仕様 v1.5 で追加された `BR-068` および `REQ-003` の `AC-003-019` / `AC-003-020` に対する要求ベースのSystem/Acceptance Test Case Specificationである。

本書は `02_FunctionalTestSpecification.md` の REQ-003 テスト群を補完し、テストケースIDは同じ `TC-F-003-*` 系列を継続する。

## 2. テストケース

### REQ-003 予約 — 生徒本人予約の所有者同一性

| TC ID | 対応AC | P | 技法 | 前提・手順 | 期待結果 | 自動化 |
|---|---|:---:|---|---|---|---|
| `TC-F-003-06` | AC-003-019 | P0 | Authorization / Data integrity | S1で認証し、公開済み将来空き枠を予約確定する。確定後のReservation所有者を内部生徒IDで確認する。 | 確定Reservationの予約者は、予約操作を行った認証済み生徒S1の内部生徒IDと一致する。氏名・メール・Google ID等ではなく内部生徒IDで所有者が確定する。 | 自動化候補 |
| `TC-F-003-07` | AC-003-020 | P0 | Tampering / Negative authorization | S1で認証した状態で、予約確定要求のクライアント入力にS2の生徒ID・氏名・メール・Google ID、または存在しない生徒識別情報を個別に混入・差し替えて確定を試みる。 | クライアント入力によってReservationの予約者をS2または存在しない生徒へ差し替えて確定できない。予約が成立する場合の所有者はS1の内部生徒IDであり、他生徒・架空生徒の予約は生成されない。 | 自動化候補 |

## 3. Defect判定観点

- 他の実在生徒へ予約所有者が誤紐付けされ、利用者境界・権限・PIIへ重大影響を与える場合は `Critical` 候補とする。
- 存在しない生徒への紐付け等、上記Critical条件に至らない予約所有者不整合は `Major` 候補とする。
- 内部所有者が正しく表示名だけが誤る場合は、所有者不整合と区別して表示系Defectとして影響範囲を評価する。
